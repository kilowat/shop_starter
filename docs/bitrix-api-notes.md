# Проверенные API этой сборки

Сборка: Bitrix 26.150.0 (SM_VERSION, `modules/main/classes/general/version.php`).

## Авторизация (`CUser`, legacy `classes/general/user.php`)

- `CUser::Login($login, $password, $remember)` — ищет пользователя строго по `U.LOGIN` (LoginInternal, user.php:1944), email не подходит. Вход по email: сначала найти пользователя по `EMAIL` (UserTable), затем вызвать `Login` с его `LOGIN`. Успех — `true`, ошибка — `['MESSAGE' => .., 'TYPE' => 'ERROR']` (в MESSAGE есть `<br>`). Капчу ядро читает напрямую из `$_REQUEST['captcha_word'/'captcha_sid']`.
- `CUser::Logout()` — снимает авторизацию, сессию и куки, включая remember-me.
- `CUser::SendPassword($login, $email, $siteId)` — статический; при пустом `$login` ищет по `EMAIL`. Неизвестный email НЕ даёт ошибки (нейтральный OK). Капча — опция `main|captcha_restoring_password`. Генерирует plaintext-checkword (`Random::getString(32)`), в `b_user.CHECKWORD` хранится хэш (`Password::hash`), письмо `USER_PASS_REQUEST` (SendImmediate, поэтому в `b_event` строк может не быть).
- `CUser::ChangePassword($login, $checkword, $password, $confirm, $siteId, $captchaWord, $captchaSid)` — экземплярный (`$USER->...`); валидирует checkword, срок его действия (policy) и сложность пароля. Ошибка — `['MESSAGE' => .., 'TYPE' => 'ERROR']`.
- `b_user.LOGIN_ATTEMPTS` инкрементится при неверном пароле (user.php:2160) и сбрасывается в 0 при успешном входе (user.php:1593) независимо от политики. Политика группы (`b_group.SECURITY_POLICY`, ключ `LOGIN_ATTEMPTS`) по умолчанию не задана → ядро капчу не требует и считает лимит 0.
- Капча: `$APPLICATION->CaptchaGetCode()` → SID, код хранится в `b_captcha`; `CaptchaCheckCode` при успешной проверке удаляет строку (captcha.php:1029) — код одноразовый. Картинка: `GET /bitrix/tools/captcha.php?captcha_sid=...`.

## Регистрация и подтверждение (проверено на этой сборке)

- `CUser::Register($login, $name, $lastName, $password, $confirm, $email, $siteId, $captchaWord, $captchaSid, $bSkipConfirm, $phoneNumber)` (user.php:2946) — штатная регистрация: капча по опции `main/captcha_registration`; подтверждение по опции `main/new_user_registration_email_confirmation` ('Y' и `new_user_email_required` != 'N') → `ACTIVE='N'` + `CONFIRM_CODE = Random::getString(8)` (plaintext); группы из `new_user_registration_def_group`; сам шлёт `NEW_USER` и `NEW_USER_CONFIRM` (SendImmediate) и сам авторизует при `ACTIVE='Y'`. `$bSkipConfirm = true` — всегда `ACTIVE='Y'` без письма подтверждения. Если включён `new_user_phone_auth` и передан телефон — шлёт SMS; в проекте телефон в Register не передаётся (сохраняется отдельно через `Update(PERSONAL_PHONE)`). Возврат: `['MESSAGE' => .., 'TYPE' => 'OK'|'ERROR', 'ID' => int]` — ключа `USER_ID` нет (user.php:3089).
- Регистрация проекта — `AuthService::register()` через `CUser::Register` (именованные аргументы; `USER_LOGIN` = e-mail), имя всегда `'Пользователь ' . random_int(10000, 99999)`. Ошибку (`TYPE=ERROR`) проверяем до чтения `ID`. Повторное письмо/`Authorize` из проекта НЕ нужны: Register сам отправляет `NEW_USER_CONFIRM` при включённом подтверждении и авторизует при `ACTIVE='Y'`. Капча: `captcha_word`/`captcha_sid` из JSON или form-data передаются в Register, проверяет ядро по опции `captcha_registration`. DTO — в `App\Auth\Dto` (`src/Auth/Dto/`): `LoginRequest`/`RegisterRequest`/`ConfirmRegistrationRequest`/`ResetPasswordRequest`/`EmailRequest`/`ProfilePayload`.
- Подтверждение: свой экшен `POST /api/auth/confirm` (`AuthService::confirmRegistration`): поиск по `EMAIL` в `Bitrix\Main\UserTable` (`b_user`; НЕ `Bitrix\Security\Mfa\UserTable` — это OTP-таблица `b_sec_user`), в `select` обязательно `CONFIRM_CODE`; сверка `hash_equals`, затем `CUser::Update(ACTIVE='Y', CONFIRM_CODE='')` и `Authorize(Context, remember)`. Повторная отправка кода (`resend`) и `EmailValidator`/`emailFromRequest` из контроллера удалены — forgot использует автовайренный `EmailRequest`. Сервисы принимают скаляры; `ProfilePayload::toFields()` → `NAME`/`PERSONAL_PHONE`.
- `CUser::CheckFields` требует e-mail при создании, если `main/new_user_email_required != 'N'`, и `NAME` — при регистрации. `UserTable::update` в ядре заблокирован (`NotImplementedException` «Use CUser class») — правки только через `CUser::Update` или SQL.
- Разделение сервисов: `AuthService` (login/logout/register/confirm/forgot/reset), `ProfileService` (update/get/deactive). `UserService` удалён. `deactive` — мягкое удаление: деактивация `ACTIVE='N'` через `CUser::Update` + `Logout` (запись физически не удаляется; `CUser::Delete` не используется). Контроллеры: `AuthController`, `ProfileController` (`/api/profile/*`), `CaptchaController` (`GET /api/captcha`).
- `$USER->Authorize(Authentication\Context, $bSave)` — D7-авторизация; `Method` enum: `Password`, `Registration`, `EmailCode`, `PhoneCode`, `External`; `$bSave = true` — remember-me; `ACTIVE='N'` не пускает.
- Неподтверждённый e-mail: `b_user.CONFIRM_CODE` + событие `NEW_USER_CONFIRM` (шаблоны есть в `b_event_message`). При `ACTIVE='N'` и непустом `CONFIRM_CODE` ядро блокирует вход (`MAIN_LOGIN_EMAIL_CONFIRM`, user.php:2134).
- Смена пароля: публичный `POST /api/auth/password/forgot` (`EmailRequest` → `AuthService::sendPasswordChangeCode` → `CUser::SendPassword` на указанный e-mail, `USER_PASS_REQUEST` с checkword), затем `POST /api/auth/password/reset` (`AuthService::resetPassword`, поиск `ID/LOGIN` в `Main\UserTable` + `CUser::ChangePassword`). Отдельного `POST /api/profile/password/change` больше нет. Plaintext-checkword есть только в письме (в `b_event` строк нет — SendImmediate); в тестах перехватывается через `OnBeforeEventSend` (обработчик `(&$arFields, &$eventMessage, $context, &$arResult)`, main/lib/mail/event.php:280).
- Удалено из проекта: SMS/телефонный вход, вход по e-mail коду, OAuth-заглушка. API ядра на будущее: `CUser::GeneratePhoneCode/VerifyPhoneCode` (TOTP в `b_user_phone_auth`, кулдаун 60 с, лимит 3); `new ShortCode(Context)->verify($code)` + `CUser::SendPassword(..., shortCode: true)` (письмо `USER_CODE_REQUEST`, эталон — `Bitrix\Main\Controller\AuthCode`); ошибки `Main\Result` читать через `getErrorCollection()->getErrorByCode()` (метода `Result::getErrorByCode` нет).

## D7-контроллеры и роуты

- Prefilters по умолчанию: `ActionFilter\Authentication` + `HttpMethod` + `Csrf` (controller.php:722). Для анонимных эндпоинтов переопределять `getDefaultPreFilters() => []`; per-action — через `configureActions()['logout']['prefilters']`.
- CSRF: `check_bitrix_sessid` (tools.php:4686) принимает `sessid` в query/post или заголовок `X-Bitrix-Csrf-Token`; из JSON-тела фильтр токен НЕ видит. При ошибке возвращает новый токен в `customData.csrf` — удобно для повторного запроса.
- Ошибки экшенов ловятся движком автоматически (`Controller::processAction` → `runProcessingThrowable`), try/catch в action не нужен. Базовый `Controllers\ApiController` (`www/local/controllers/ApiController.php`) переопределяет `runProcessingThrowable()` + `finalizeResponse()`: `AuthException` → `AUTH_ERROR`/400, `AccessDeniedException` → `ACCESS_DENIED`/403, `SystemException` → `BUSINESS_ERROR`/400, прочее → `INTERNAL_ERROR`/500 (generic message, без внутренностей); `BinderArgumentException`/`ValidationException` отдаются штатному обработчику с HTTP 400. Все контроллеры (`Auth`/`Basket`/`Profile`/`Captcha`) наследуют `ApiController`.
- В dev (`exception_handling.debug=true` в `local/.settings_extra.php`) движок добавляет вторым error отладочный стек — приватный `processExceptionInDebug`, не переопределяется; в prod (`debug=false`) остаётся только чистая ошибка. Логирование исключений движок делает сам.
- Автовайр DTO: `getAutoWiredParameters()` + `ValidationParameter(Dto::class, fn() => Dto::fromRequest(...))`; валидация — один слой, атрибуты DTO (`ValidationService` вызывается внутри `ValidationParameter`). Обязательность неявная, из типа: не-nullable параметр конструктора без дефолта = обязательный; не передан (или JSON null) → `BinderArgumentException` с ошибками по ключам полей («Поле «email» обязательно для передачи», код = ключ с учётом `#[Key]`), автовайр отдаёт 400. Nullable без дефолта → маппер подставляет null; единственный дефолт в Auth-DTO — `bool $remember = true`. Атрибут `RequiredOn` удалён. Правила этой сборки: `#[Min]`/`#[Max]` — ТОЛЬКО числа (для строк `#[Length(min:)]`); `#[Email]` отклоняет пустую строку (`check_email('') === false`); `#[Phone]` отклоняет `''` (null пропускается: `ValidationService` не валидирует null, ValidationService.php:160); `#[RegExp()]` без pattern бросает ArgumentCountError. Пустые значения обязательных полей ловятся валидацией ('' не проходит Email/NotEmpty/Length). Санитайзинг — opt-in: без `#[Sanitize]` значение не трогается (пароли — без атрибута), `Filter::Raw` тоже пропускает; Trim/StripTags только явные (например, `name` в `ProfilePayload`). Email/code/checkword/phone/coupon не тримсятся.
- Ответы API: все write-операции Auth/Profile — void, ядро отдаёт `{"status":"success","data":null,"errors":[]}` (ajaxjson.php:56); данные пользователя — только `GET /api/auth/me` (плоский `{id, name, full_name, email}`, без обёртки `user`; Swagger-схема `AuthUser`). Swagger — схемы `SuccessResponse` (200) и `ErrorResponse` `{status, data, errors[]}` (400/401). Сервисы не нормализуют вход (каст типов делает RequestMapper, санитайзинг — только по явному `#[Sanitize]`).
- Свой action-фильтр по образцу `ActionFilter\Csrf`: `extends Base`, `onBeforeAction(Event)`, запрос — `$this->getAction()->getController()->getRequest()`, отказ — `addError(new Error(msg, code, customData))` + `new EventResult(EventResult::ERROR, null, null, $this)`. `customData` попадает в JSON ошибки.
- Капча: `App\Helper\Captcha\CaptchaService` (generate/check/url поверх `$APPLICATION->CaptchaGetCode/CaptchaCheckCode`, коды в `b_captcha`, sid одноразовый) + `App\Helper\Captcha\CaptchaActionFilter` (prefilter из `configureActions()`; сейчас НЕ навешен ни на один экшен — login/confirm идут без капчи, register проверяет её ядром по опции `captcha_registration`). Генерация — `CaptchaController::captchaAction` (`GET /api/captcha`) поверх `CaptchaService::generate()`. Счётчики (`LoginAttempts`) и кеш удалены; ядро само ведёт `b_user.LOGIN_ATTEMPTS` (user.php:1593/2160), проект не использует. `Controller::init()` сразу вызывает `configureActions()` (controller.php:144).
- CSRF обязателен только для `logout` и `/api/profile/*` (prefilters `Authentication` + `HttpMethod POST` + `Csrf`); login/register/confirm/forgot/reset — публичные (`getDefaultPreFilters() => []`). `sessid` передаётся в query/form-data или заголовком `X-Bitrix-Csrf-Token`.
- «Запомнить меня» — без кеша: флаг напрямую в `CUser::Login($login, $pass, $remember 'Y'/'N')` и `CUser::Authorize($context, $bSave)` (user.php:1525). `$bSave=true` → `setStoredAuthCookies` ставит `UIDH`/`UIDL` (~1 год, user.php:1708); `false` → эти cookie не ставятся вовсе (user.php:1601 `if ($bSave || auth_multisite)`). Перенос флага регистрация→подтверждение удалён: confirm использует свой `remember` из запроса.

## Swagger

- swagger-php 7 (новый namespace `OpenApi\Spec`): `OA\Operation\Get/Post`, `OA\RequestBody`, `OA\MediaType`, `OA\Schema`, `OA\Property(property:..., schema: new OA\Schema(...))`, `OA\Response`, `OA\Parameter`, `OA\Tag`. У `OA\Property` в этой версии НЕТ параметра `example` — пример/тип задаются вложенным `#[OA\Schema(type: ..., example: ...)]`, иначе свойство молча выпадает из спецификации (так были сломаны схемы Basket/Auth до актуализации). Ошибки описываются ссылкой на схему `ErrorResponse` через `content: new OA\Schema(ref: ErrorResponse::class)`.
- Спецификация собирается на лету: `GET /swagger/openapi.json` (сканирует `/local/controllers` и `/local/src/Swagger`, конфиг — `local/src/Swagger/router.php`).

## Сессии/куки (проверено HTTP-тестами)

- Авторизация живёт в PHPSESSID + remember-me куках; logout их гасит. Тесты curl: сохраняйте куки и после logout (`-c`), иначе jar со старыми remember-куками «оживит» сессию.
